# 로드맵과 현실 점검

## 지금 있는 것 (0단계 — 이 저장소)

- 주소/검색어 판정, 문법 파서, 순위 엔진 — 의존성 없는 순수 모듈 (`src/core/`)
- 테스트 29개 (`npm test`)
- 브라우저에서 만져볼 수 있는 프로토타입 (`npm run dev`)

엔진(렌더링)은 없다. **주소창 동작만** 진짜로 만들어 둔 상태다.
순서를 이렇게 잡은 이유: 차별점이 주소창이면, 크로미움을 빌드하기 전에
주소창이 실제로 좋은지부터 확인하는 게 맞다.

## 1단계 — 확장 프로그램으로 먼저 검증 (1~2개월)

크로미움 확장(`chrome.omnibox`는 제약이 많으므로 `commands` + 콘텐츠 스크립트 오버레이)으로
명령 바만 배포한다. `src/core/`를 그대로 쓴다.

- 목적: **"이걸 매일 쓰는 사람이 존재하는가"** 하나만 확인
- 지표: 설치 후 7일 리텐션, 하루 명령 바 호출 횟수, `!`/`@` 사용 비율
- 이 단계에서 리텐션이 안 나오면 브라우저를 만들 이유가 없다. 여기서 멈추는 게 이득이다.

## 2단계 — Electron 셸 (2~3개월)

`WebContentsView` 기반의 진짜 브라우저 창. 확장으로는 못 하는 것들이 여기서 열린다.

- 탭 생성 자체를 가로채는 중복 방지 (확장은 탭 생성 후에만 개입 가능)
- 주소 표시줄 완전 대체 (구조 칩, 파라미터 토글)
- 화면 분할, 세션 저장
- 트레이드오프: 크로미움 엔진 업데이트를 Electron 릴리스에 의존하게 된다. 보안 패치 지연이 리스크다.

## 3단계 — 자체 셸 (6개월+)

CEF 또는 크로미움 직접 빌드. **여기까지 오기 전에 1·2단계에서 수요가 증명되어야 한다.**
브라우저 엔진 유지보수는 상시 인력이 붙는 일이고, 대부분의 브라우저 스타트업이
여기서 소진된다.

---

## 냉정한 부분

창업 관점에서 먼저 말해둘 것들이다. 제품이 틀렸다는 뜻이 아니라, 이 순서를 알고 시작하자는 뜻이다.

**1. 주소창만으로는 브라우저를 바꾸게 만들지 못한다.**
전환 비용은 비밀번호, 확장, 북마크, 습관이다. "주소창이 낫다"는 이유로 브라우저를
갈아타는 사람은 매우 적다. 그래서 1단계를 확장으로 잡았다. 전환 비용 0에서 가치를 먼저 증명한다.

**2. Arc가 비슷한 걸 시도했고 접었다.**
Arc는 Command Bar를 만들었지만 동시에 브라우저 UI 전체를 바꿨다. 학습 비용이 너무 컸다.
교훈: **기존 브라우저와 똑같이 생겼는데 주소창만 다른 것**이 이기는 전략이다. 바꾸는 건 한 개면 된다.

**3. 수익 모델이 검색 트래픽이면 안 된다.**
검색 제휴 수익을 받는 순간 "웹 검색을 마지막 줄에 두는" 원칙과 충돌한다.
원칙이 곧 차별점이므로 여기서 타협하면 제품이 사라진다. 대안:
- 팀/기업용 유료 (공유 별칭, 사내 호스트 규칙, 세션 공유) ← 가장 현실적
- 개인 구독 (기기 간 동기화, 세션 히스토리)
- 로컬 우선이라는 점을 앞세운 프라이버시 포지셔닝

**4. 초기 지표는 DAU가 아니라 "명령 바 호출 / 사용자 / 일"이다.**
이 숫자가 하루 10회를 넘으면 습관이 된 것이고, 3회 아래면 아직 아니다.
